## 0. Start here

Questions this document answers:

1. What exactly is the difference between the **NIC** and **tap0**?
2. Why do people reach for **virtio**, beyond "fewer VM exits"?
3. How does a packet **flow to and from the guest**, step by step?
4. What does all of this look like in the **seven OSI layers**?
5. How do **Windows, macOS and Linux** differ, and where does **Multipass** sit?

### The whole story in eight sentences

If you read nothing else, read this, then come back for the pictures.

1. The guest runs an ordinary OS with an ordinary network stack. It believes it owns a network card.
2. That "card" is **software inside the VMM** (host userspace): a set of registers and queues. The guest only has a **driver** for it.
3. To send, the driver builds an **Ethernet frame** in guest RAM, describes it in a shared ring, and writes one **doorbell** register. That write is the only VM exit.
4. The VMM copies the frame out of guest RAM and `write()`s it into a **TAP file descriptor**. The TAP device (`tap0`) is the **host kernel's end of the virtual cable**.
5. From there it is an ordinary host network: `tap0` is a port on a **bridge** (layer 2) and/or the host **routes and NATs** the packet (layers 3 and 4) out of the physical NIC.
6. Replies take the same path backwards: the kernel queues the frame on `tap0`, the VMM's receive thread `read()`s it, copies it into a free guest buffer, and **injects an interrupt**.
7. So the virtual NIC and `tap0` are **the two ends of one virtual cable**, and the VMM is the cable.
8. **virtio** is the standard *shape* of the guest's end of that cable: rings in shared memory, designed for software on the other side.

## 1. Networking from first principles

### 1.1 A packet is nested structs

To a C engineer, the seven-layer model is encapsulation: each layer wraps the one above in a
header. Here is the 74-byte frame that tinyvm's guest sends for one `ping`:

```
 offset 0               14                      34              42                         74
        +---------------+-----------------------+---------------+--------------------------+
        | Ethernet (L2) | IPv4 (L3)             | ICMP echo     | payload                  |
        | dst MAC       | version, length, TTL, | type=8 (req), | 32 bytes                 |
        | src MAC       | protocol=1 (ICMP),    | code, checksum|                          |
        | ethertype     | header checksum,      | id, seq       |                          |
        |   0x0800      | src IP, dst IP        |               |                          |
        +---------------+-----------------------+---------------+--------------------------+
        14 bytes          20 bytes                8 bytes         32 bytes
```

In C, that really is just structs (these are in [`netproto.h`](netproto.h)):

```c
struct __attribute__((packed)) EthHdr  { uint8_t dst[6]; uint8_t src[6]; uint16_t ethertype; };
struct __attribute__((packed)) Ipv4Hdr { uint8_t ver_ihl, tos; uint16_t total_len, id, frag;
                                          uint8_t ttl, proto; uint16_t csum; uint8_t src[4], dst[4]; };
struct __attribute__((packed)) IcmpEcho{ uint8_t type, code; uint16_t csum, id, seq; };
```

`build_icmp_echo()` in `netproto.h` is, in about 30 lines, what the guest's TCP/IP stack does when you ping:
fill the inner struct, wrap it in the next one outward, compute the checksums. Receiving is the same in reverse: parse
the outer header, then the next, then the next. (ICMP is a helper protocol of IP; for web traffic this slot
would be TCP or UDP, layer 4, with ports instead of type/code.)

Each layer answers a different question about the same bytes:

| Layer | Header | The question it answers | Scope of the answer |
|---|---|---|---|
| **L7** Application | (the payload) | what is the program saying? | between programs |
| **L4** Transport | TCP/UDP: ports | which *program* on the destination machine? | end to end |
| **L3** Network | IP: addresses, TTL | which *machine*, and which way to get there? | end to end |
| **L2** Data link | Ethernet: MAC addresses | which device is the **next hop on this one link**? | one link only |
| **L1** Physical | voltages, light, radio | how do bits cross this wire? | one link only |

The L2 row is the one people get wrong: **an Ethernet header is rewritten at every hop**, because a
MAC address only means "the next device on this link". The IP header survives end to end.

### 1.2 What each device looks at

| Device | Looks at | Decides | In our setup |
|---|---|---|---|
| **NIC** | L2 frames (and L1) | sends and receives frames; filters by MAC; computes the frame check sequence | physical NIC, virtio-net, the toy NIC |
| **Switch / bridge** | destination MAC (L2) | which *port* to forward to | `tvmbr0` |
| **Router / host IP stack** | destination IP (L3) | which next hop and which interface | the host forwarding 10.0.2.15's packets |
| **NAT** | IP + ports (L3/L4) and remembered state | rewrite addresses/ports, and undo it for replies | the `masquerade` rule + conntrack |
| **Firewall** | anything, usually stateful | allow or drop | nftables / iptables |

### 1.3 Two kinds of address in one packet, and why ARP exists

The guest wants to reach 10.0.2.1. IP says *who* (10.0.2.1), but Ethernet needs *which device on
this link*: a MAC. **ARP** bridges the two: the guest broadcasts "who has 10.0.2.1?" (destination MAC
`ff:ff:ff:ff:ff:ff`, which every device on the link receives) and the owner answers "10.0.2.1 is at
`<MAC>`". The guest caches it. That is the first thing `PingDemo::resolve_gateway()` does, and it is why the
first frame on the wire is not a ping at all.

### 1.4 What a real NIC does (so virtual ones make sense)

A modern NIC does not make the CPU push bytes through a register. It works with **rings in RAM**, in a
design every Ethernet driver shares:

```c
struct tx_desc { uint64_t buf_addr; uint16_t len; uint8_t cmd; uint8_t status; };  /* simplified, e1000-style */
struct tx_ring { struct tx_desc desc[N]; uint32_t head, tail; };

/* driver:  fill desc[tail]; tail = (tail + 1) % N; write the NIC's TAIL register     <- the DOORBELL */
/* NIC:     DMA-read desc[head], DMA-read the buffer, put the frame on the wire,
            set status = DONE, head++, raise an INTERRUPT                              */
```

Three ingredients: **descriptor rings in RAM**, a **doorbell** register write, and an **interrupt**.
Keep these three in mind: **virtio is the same idea, standardised for the case where the "NIC" is software.**
The toy NIC in this project is the *older* design, where the CPU copies every byte through a register, and exists so you can feel the difference.

## 2. What a VM changes

### 2.1 Only layer 1 disappears

![The same layers, physical and virtual](docs/img/02_osi_physical_vs_virtual.png)

Read the red path left to right. The guest builds a genuine Ethernet frame (layers 7 to 2, all real). The "wire"
between the virtual NIC and `tap0` is a **memory copy plus a syscall**. That is layer 1 reduced to nothing: no
voltage, no clock, no signal encoding. From `tap0` onward it is an ordinary host network: a bridge
(L2), the host's IP stack doing routing and NAT (L3/L4), a physical NIC (L2), a real wire (L1).

The boundary between guest and host is exactly an **L2 unit**: the guest hands over a complete Ethernet frame.
Nothing above L2 is virtualised. That is why a guest can run any OS and any protocol.

### 2.2 Four things that all get called "the NIC"

This is where the confusion comes from. There are four different objects in the chain:

| # | Object | Lives in | Who talks to it | Has a MAC? |
|---|---|---|---|---|
| a | the guest's `eth0` and its **driver** | guest kernel | the guest's IP stack | the guest MAC (read from the device's config space) |
| b | the **virtual NIC** (device model) | the VMM, in host userspace (or a kernel thread with vhost) | the guest driver (registers + rings); the back-end (a function call) | advertises the guest MAC |
| c | **`tap0`** | host kernel, a `net_device` | the VMM (`read`/`write` on an fd); the bridge or IP stack, as an ordinary interface | its own MAC, unused once it is a bridge port |
| d | the **physical NIC** (`eth0`/`wlan0` on the host) | hardware plus its driver | the host's bridge or IP stack | its real MAC |

### 2.3 NIC vs tap0: two ends of one cable

![Where each piece runs](docs/img/01_execution_modes.png)

- The **virtual NIC (b)** is the **guest's end** of the cable. It exists because the guest needs *hardware* to drive: a guest kernel cannot call into the host kernel, it can only touch device registers and shared RAM.
- **`tap0` (c)** is the **host's end**. It exists because the host kernel needs a *network interface* to route, bridge, firewall and `tcpdump`: `tap0` is how a frame becomes an ordinary object in the host's networking.
- The **VMM is the cable**. In userspace it translates between two worlds: it reads rings in guest RAM (the guest's world) and `read()`/`write()`s a file descriptor (the kernel's world).

Why not skip `tap0` and have the VMM send out of the physical NIC directly? Then the VMM would
have to implement bridging, routing, NAT, DHCP and firewalling itself. That is exactly what user-mode
networking (SLIRP, our `GatewayBackend`) does, and it is why that mode is simple, needs no root, and is slower and less capable. With `tap0`, the VMM reuses the kernel's entire networking stack for free.

Two smaller facts:
- **TAP vs TUN:** TAP carries Ethernet frames (layer 2), TUN carries IP packets (layer 3). A NIC needs TAP, because the guest brings its own MAC address and does its own ARP.
- **`IFF_NO_PI`**, the flag in `TapBackend`, means "no extra packet-info header: just the raw frame". (A real VMM also sets `IFF_VNET_HDR` so offload metadata travels with the frame; see section 4.5.)

## 3. Packet journeys

The cast, from the demo: the **guest** (MAC `52:54:00:12:34:56`, IP 10.0.2.15) and its **gateway**
10.0.2.1, which on the TAP back-end is the host's bridge `tvmbr0`.

### 3.1 Journey 1: the guest sends

![Journey 1: the guest sends](docs/img/03_journey_tx.png)

| # | What happens | OSI | In the code |
|---|---|---|---|
| 1 | The application calls `sendto()`. The guest kernel builds the L4/L3 headers, picks the route (the gateway), finds its MAC in the ARP cache, and adds the Ethernet header | L7 to L2 | `net::build_icmp_echo()` plays this role in tinyvm's guest |
| 2 | The kernel hands the finished frame to the driver | L2 | `PingDemo` calls `nic.send()` |
| 3 | The driver copies the frame and a 12-byte `virtio_net_hdr` into a buffer in guest RAM, fills two descriptors, writes the head into the available ring, and **release-stores** `avail.idx` to publish it | L2 | `VirtioNetDriver::send()` |
| 4 | The driver writes the **QueueNotify** register (the doorbell). That store targets an address with no RAM behind it, so the CPU leaves guest mode: a **VM exit** | hardware | same function, last line before polling |
| 5 | KVM sees an MMIO exit and returns from `KVM_RUN` to the VMM | host | `Vcpu::run_loop`, `case KVM_EXIT_MMIO` |
| 6 | The device model, holding its mutex, **acquire-loads** `avail.idx`, reads the descriptor chain (copy once, validate every address), and gathers header + frame from guest RAM | L2 | `VirtioNetMmio::process_tx_locked()` |
| 7 | The back-end writes the frame into the TAP fd: a syscall that copies it into the kernel | the cable | `TapBackend::send()` |
| 8 | `tap0` delivers the frame to the host as if it came off a cable. A bridge forwards it by destination MAC, or the IP stack routes and NATs it, and a NIC driver puts it on the wire | L2 to L1 | the host kernel; see `lab/net-lab.sh` |
| 9 | The device model **release-stores** `used.idx`; the VMM calls `KVM_RUN` again (**VM entry**). The driver sees `used.idx` advance and frees the buffer | L2 | `push_used()`; the loop in `run_loop` |

### 3.2 Journey 2: a packet arrives for the guest

![Journey 2: a packet arrives](docs/img/04_journey_rx.png)

| # | What happens | OSI | In the code |
|---|---|---|---|
| 1 | A frame arrives from the outside world | L1/L2 | host NIC |
| 2 | The NIC driver passes it up. conntrack reverses the NAT (destination IP back to 10.0.2.15). Routing picks the bridge; the bridge finds the guest's MAC behind `tap0` | L3/L4, L2 | host kernel |
| 3 | `tap0` queues the frame for its file descriptor, which becomes readable | the cable | host kernel |
| 4 | The VMM's RX thread, blocked in `poll()`, wakes and `read()`s the frame | the cable | `TapBackend::rx_loop()` |
| 5 | The device model, under its mutex, takes a **free receive buffer** from the available ring (the guest pre-posted it), writes header + frame into guest RAM, writes the used entry, and release-stores `used.idx` | L2 | `VirtioNetMmio::deliver_rx()` |
| 6 | The VMM tells KVM to **inject an interrupt** (`KVM_IRQ_LINE`, or an `irqfd`) | hardware | not implemented in tinyvm: the guest polls |
| 7 | The CPU delivers the interrupt to the guest (KVM may have to kick the vCPU out of guest mode to do so, or use hardware posted interrupts) | hardware | n/a |
| 8 | The driver acquire-loads `used.idx`, reads the frame, builds a buffer for the stack, and passes it up L2 to L3 to L4 to the socket. It re-posts the buffer | L2 up to L7 | `VirtioNetDriver::recv()` |

**Notice the asymmetry.** Sending needs a VM exit (the doorbell). Receiving does **not** need one for the frame
itself: the VMM writes into guest RAM from the outside, and an ordinary interrupt tells the guest. If the guest has no free buffer posted, the device has nowhere to put the frame and **must drop it**
(`rx_dropped_no_buffer` in the report).

### 3.3 What actually crosses the wire for `ping 10.0.2.1`

Four frames. The first two are ARP, the last two are the ping itself:

| # | Direction | Ethernet dst | Contents | Size |
|---|---|---|---|---|
| 1 | guest to wire | `ff:ff:ff:ff:ff:ff` (broadcast) | ARP request: who has 10.0.2.1? tell 10.0.2.15 | 42 B |
| 2 | wire to guest | guest MAC | ARP reply: 10.0.2.1 is at `<gateway MAC>` | 42 B |
| 3 | guest to wire | gateway MAC | IPv4 ICMP echo request, src 10.0.2.15, dst 10.0.2.1 | 74 B |
| 4 | wire to guest | guest MAC | ICMP echo reply | 74 B |

(Real Ethernet pads short frames to 60 bytes in the NIC hardware; on a virtual link nothing needs padding.)

### 3.4 Going beyond the gateway: NAT, and what changes at each hop

![What changes at each hop](docs/img/06_headers_per_hop.png)

When the guest pings `1.1.1.1`, the **IP destination is 1.1.1.1** but the **Ethernet destination is still the
gateway's MAC**: the guest only needs the *next hop*, not the final destination. At the host, the L2 header is
thrown away and rebuilt for the next link (new MACs), and **NAT rewrites the source IP** from 10.0.2.15 to the host's
address, because a private address means nothing on the internet and the reply would never find its way back.
The host remembers the translation (conntrack) and on the reply rewrites the destination back, then forwards by MAC to
the guest. Three rules fall out:

- **L2 header:** rewritten at every hop.
- **L3 header:** end to end, except where NAT deliberately rewrites it.
- **L4/L7:** untouched by switches and routers (NAT may rewrite ports).

## 4. Emulated NIC vs virtio: why people reach for virtio

### 4.1 A correction to the earlier README

An earlier version of this project's README said the exit counts were "the whole argument for virtio".
That overstated it, and you were right to suspect there is more. Two honest points:

- The **toy NIC** is deliberately primitive (CPU copies bytes through a register), so its numbers exaggerate.
  **Emulated real NICs such as the Intel e1000 already use descriptor rings** (section 1.4), so their exit count is much closer to virtio's than the toy NIC's.
  They still cost extra exits for things like interrupt masking and acknowledging, but I have not measured how many, so I won't quote a number.
- VM exits are **one** reason among several.

### 4.2 The real reasons

| Axis | Emulating a real chip (e1000, rtl8139) | virtio-net |
|---|---|---|
| **Design goal** | imitate silicon that was designed for a physical wire | designed for the case where the other side is software |
| **What must be reproduced** | hundreds of registers, their quirks, timing assumptions, errata the guest driver depends on | a small, written specification: a few registers, feature bits, rings |
| **Guest driver** | the guest OS must ship a driver for that exact chip | one driver per OS; Linux has it built in, Windows has the virtio drivers, the BSDs too; the same driver works on QEMU, Firecracker, Apple's Virtualization framework and others |
| **Attack surface** | large device model, large attack surface | small, well-defined surface (but still hostile input, see `dma.h`) |
| **VM exits per frame** | rings help, but interrupt-handling register accesses add exits | one doorbell per batch, and either side can ask the other to suppress notifications |
| **Offloads and big frames** | whatever the emulated chip supports | `virtio_net_hdr` carries checksum and segmentation metadata, so frames of up to ~64 KiB can cross the guest-host boundary without being cut into 1500-byte pieces or checksummed (4.5) |
| **Back-end flexibility** | tied to the device model's code | the same ring can be served by the VMM, by a **kernel thread (vhost-net)**, or by a **userspace switch (vhost-user, e.g. DPDK/OVS)**, without changing the guest |
| **Scaling** | one queue pair | multiple queue pairs, e.g. one per vCPU |
| **Evolution** | frozen with the chip | features are negotiated bit by bit, so old drivers and new devices interoperate |

So the summary for an interview is: *virtio replaces "imitate a chip" with "a small standard for shared-memory queues", and that wins on exits, on code size and security, on guest compatibility, on offloads, and on letting the data path move into the kernel or a userspace switch.*

### 4.3 Inside one virtqueue

![Inside one virtqueue](docs/img/05_virtqueue.png)

A virtqueue is three arrays in guest RAM; the picture shows one ping going out. In C (`abi.h`, `guest/virtio_driver.h`):

```c
struct Desc      { uint64_t addr; uint32_t len; uint16_t flags; uint16_t next; };   /* flags: NEXT, WRITE */
struct AvailRing { uint16_t flags, idx, ring[N], used_event; };   /* driver -> device: heads of chains offered */
struct UsedRing  { uint16_t flags, idx; struct { uint32_t id, len; } ring[N]; uint16_t avail_event; };
```

The protocol is "fill, then publish the index":

- **Driver:** write the descriptors and the buffer contents with ordinary stores, then **release-store** `avail.idx`.
- **Device:** **acquire-load** `avail.idx`, then read the ring entry and descriptors.

The release/acquire pair is what guarantees the device never sees the new index with stale entries (on
ARM this ordering is *not* automatic, which matters for Apple silicon). Each side only ever writes its own index.
The **handshake** before any of this (`init()` in the driver, `write_status()` in the device) is: reset, ACKNOWLEDGE, DRIVER,
negotiate features, FEATURES_OK, set up the queues, DRIVER_OK; it is what the Linux kernel does when it finds a virtio device.

### 4.4 Where the cable can move: vhost

In the design so far, the VMM process handles every doorbell and copies every frame. For speed, the data path can be moved **out of the VMM** without the guest noticing:

- **vhost-net:** a kernel thread processes the virtqueues directly and talks to the TAP device in-kernel. The doorbell is delivered through an **`ioeventfd`** (KVM turns the write into an eventfd signal; the guest still exits, but only to the kernel, not up to userspace) and interrupts through an **`irqfd`** (an eventfd write that makes KVM inject the interrupt). The VMM keeps only the control plane (setup, negotiation).
- **vhost-user:** the rings are served by a separate userspace process (a DPDK or Open vSwitch data path) over shared memory.

The guest sees the same virtio device in all cases. This is why the **front-end/back-end split** matters: the front-end (virtio) is what the guest depends on; the back-end can be swapped.

### 4.5 Offloads, and why guest to host is special

Most guest traffic crosses only host memory before reaching another VM or the host, never a real wire. Two things follow:

- **Checksums** protect against corruption on a wire. In memory there is no wire, so computing one in the guest only for it to be verified in the host is wasted work. `virtio_net_hdr` has `flags`, `csum_start`, `csum_offset` so the guest can say "checksum not computed; finish it when it leaves".
- **Segmentation (GSO/TSO):** the guest can hand over a 64 KiB TCP chunk with `gso_type` and `gso_size` and let the host (or the physical NIC) split it into 1500-byte frames later: one trip through the machinery instead of ~44.

Our device negotiates **only** `VERSION_1` and `MAC`, so none of this is implemented: the header is 12 zero bytes. These are
the features a production device adds on top of this skeleton.

### 4.6 The contrast, measured in tinyvm

For the same 8 frames (1 ARP + 3 pings out, 1 ARP reply + 3 echo replies in), the in-process harness counted
register accesses (each a VM exit on real KVM): **161 for the toy NIC** (4 setup, about 157 moving bytes and polling) versus
**50 for virtio-net** (42 one-time handshake, then **8**: one doorbell per frame). Virtio's cost is a fixed setup bill;
the toy NIC's grows with every byte. Remember 4.1: the toy NIC is the extreme case, not what e1000 costs.

## 5. Platforms, and where Multipass sits

![Same front-end, different back-ends](docs/img/07_front_and_back_ends.png)

**What stays the same on every host:** the guest sees a virtio-net device (for Ubuntu guests the driver is built in), builds Ethernet frames, does ARP and IP. **What changes:** the **back-end**, i.e. how frames reach the outside world, and the **hypervisor API** that runs the vCPUs.

| Host | Hypervisor API (CPU and memory only) | Typical network back-ends |
|---|---|---|
| **Linux** | **KVM** (`/dev/kvm`, ioctls: what tinyvm uses) | TAP + bridge (+ NAT, + dnsmasq for DHCP/DNS), vhost-net, user-mode (SLIRP), macvtap |
| **Windows** | **WHPX**, the Windows Hypervisor Platform: user-mode partition APIs in front of Hyper-V's hypervisor; or Hyper-V itself through its management stack | Hyper-V **virtual switch** (the "Default Switch" does NAT, an "external" switch bridges to a physical NIC); with QEMU, a TAP-Windows adapter or user-mode networking |
| **macOS** | **Hypervisor.framework** (vCPU and memory only, no devices); or Apple's higher-level **Virtualization.framework** | `vmnet.framework` (shared = NAT, host-only, bridged; used by QEMU), Virtualization.framework's built-in NAT/bridged attachments, user-mode |

None of the three hypervisor APIs gives you a network. The VMM supplies the device (front-end) and connects it to something host-specific (back-end). That is the same split as `NetBackend` in this project.

**Where Multipass fits.** Multipass is a command-line client plus a daemon that launches Ubuntu VMs. It does not
implement virtualization: it drives a hypervisor per platform behind a common interface, and handles images,
cloud-init provisioning, and networking on top. Your take-home answer said "decouple implementation logic into
interfaces is what enables cross-platform usability": this is where that applies, and `NetBackend`
is a small instance of the same pattern. Things to **verify in the current Multipass documentation and source** before the interview, rather than trusting my memory:

- which backend is the default on each OS and how to switch (`multipass get local.driver` / `multipass set local.driver=...`);
- how extra network interfaces are requested (`multipass networks`, `multipass launch --network ...`);
- on Linux with QEMU, what bridge and rules the daemon creates (look at `ip link` and `nft list ruleset` on a machine running it: expect something like what `lab/net-lab.sh` builds);
- the name and shape of the C++ interface behind the backends (I believe `VirtualMachineFactory` in the `canonical/multipass` repository, but check).

## 6. Your take-home answer, annotated

The question: *"Describe your level of understanding of networking, especially virtual networking on Windows, macOS and Linux."*
Your answer was honest (it said where you were strong and where you were not) and it already contained the right
instinct about ring buffers. Here is what was right, and what to fix:

> *"the Virtual Machine Manager like QEMU provides a virtual network card."*

**Right.** More precisely, the VMM provides the **device model**: the registers and queues the guest driver talks to.

> *"KVM runs guest code in kernel space until it encounters a VMEXIT that requires packet processing"*

**Fix.** Guest code does not run in *kernel space*. It runs in **guest mode** (VMX non-root): the CPU executes it
directly, in a hardware-isolated context. The host kernel gets control only on a **VM exit**, and the exit is caused
by the guest touching something it cannot handle alone (a doorbell write), not by "packet processing" as such. (Figure 1.)

> *"(Of course this is oversimplified because modern VMs use ring buffers and don't VMEXIT every time a packet arrives)"*

**Right, and the key insight.** Sharpen it: with rings, **sending** costs one exit per batch (the doorbell), and **receiving** costs **no exit for the frame**: the VMM writes into guest RAM and an interrupt is injected.

> *"This is then handed over to QEMU which has implemented a virtual networking device"*

**Right.** KVM returns from `KVM_RUN` to the VMM, which handles the access.

> *"that then receives packets from the actual network card"*

**Fix.** The VMM does not read from the physical NIC. It reads from its **back-end**: usually a **TAP device**, which the host kernel feeds after bridging, routing and NAT. The physical NIC is the host kernel's business (unless you use device passthrough, which is a different design).

> *"and then hands these over to the guest virtual NIC in the virtual machine which then processes the packet"*

**Fix.** The virtual NIC is **not inside the VM**: it is code in the VMM. Inside the VM there is the **driver** and the guest's own network stack, which does the processing (L2 up to L7).

> *"and returns control back to KVM."*

**Fix.** The VMM re-enters the guest by calling `KVM_RUN` again; control goes back *into the guest*.

### A stronger answer (adapt it to your own voice)

> "In a VM the guest has a virtual NIC, which is really a device model in the VMM. The guest driver and the device share
> virtqueues in guest RAM, as in virtio-net. To transmit, the driver writes a frame into a buffer, publishes it in the
> available ring and rings a doorbell register; that write is a VM exit, and KVM returns to the VMM, which copies the frame
> and writes it to a back-end, normally a TAP device. On Linux the TAP is a port on a bridge or the host routes it with NAT; the
> host kernel does the rest. Receiving is the reverse: the VMM reads the TAP fd, copies the frame into a buffer the guest
> posted, and injects an interrupt, so no VM exit is needed for the frame itself. vhost-net can move that data path into a
> kernel thread. Windows and macOS use the same front-end with different back-ends: Hyper-V's virtual switch on
> Windows, vmnet or the Virtualization framework on macOS. I have built a small version of this: a KVM-based VMM in C++ with
> a TAP back-end, a virtio-net device model and a guest driver, behind a back-end interface. I have not yet worked with the Windows or macOS native APIs."

That last sentence replaces "I have not yet implemented a virtual networking backend". It becomes true once you have run tinyvm and can explain every step in sections 3 and 4 without the diagrams; say it only then, because an interviewer will ask you to walk through it.

## Appendix A: glossary

| Term | Meaning |
|---|---|
| **Frame / packet** | a frame is the L2 unit (Ethernet header + payload); a packet is the L3 unit (IP header + payload), carried inside a frame |
| **MAC address** | 6-byte L2 address of a NIC; identifies the next hop on one link |
| **ARP** | maps an IPv4 address to a MAC on the local link |
| **Bridge / switch** | an L2 device that forwards frames by destination MAC |
| **NAT (SNAT, masquerade, DNAT)** | rewriting IP addresses and ports; SNAT/masquerade changes the source on the way out, DNAT changes the destination (used for replies and port forwards) |
| **conntrack** | the kernel's connection table, which lets NAT undo itself on replies |
| **TAP / TUN** | a virtual interface whose cable is a file descriptor; TAP = Ethernet frames, TUN = IP packets |
| **NIC** | network interface controller: moves frames between memory and the wire |
| **DMA** | a device reading or writing RAM by itself, without the CPU copying each byte |
| **MMIO / port I/O** | the two ways the CPU talks to device registers; each access by a guest is a VM exit |
| **Doorbell** | a register write that says "I have put work in the ring" |
| **VM exit / entry** | the CPU leaving guest mode for the host (exit), and going back (entry, `KVM_RUN`) |
| **Virtqueue** | virtio's shared-memory ring set: descriptor table, available ring, used ring |
| **Front-end / back-end** | the device the guest sees / how the host moves the frames |
| **vhost-net / vhost-user** | moving the virtqueue processing into a kernel thread / into another userspace process |
| **ioeventfd / irqfd** | KVM mechanisms: a guest write signals an eventfd (no trip to userspace); an eventfd write injects a guest interrupt |
| **SLIRP / user-mode networking** | the VMM itself pretending to be the network; no root needed |
| **GSO / TSO** | segmentation offload: send a big TCP chunk and split it into frames later |
| **MTU** | the largest payload an L2 link carries (1500 for standard Ethernet) |
| **NAT mode vs bridged mode** | a private subnet behind NAT, versus the VM appearing as a peer on the physical LAN |

## Appendix B: interview cheat sheet

1. **NIC vs tap0?** The virtual NIC is the guest's end of the cable (a device model the guest driver talks to); tap0 is the host kernel's end (a netdev the kernel can bridge or route); the VMM copies frames between them.
2. **Why virtio?** A small standard for shared-memory queues instead of imitating a chip: fewer exits and notifications, a smaller device model and attack surface, one guest driver everywhere, offloads and large frames, and the data path can move into the kernel (vhost-net) or a userspace switch.
3. **Does receiving cause a VM exit?** Not for the frame: the VMM writes into guest RAM and an interrupt is injected. Sending costs one exit per batch (the doorbell).
4. **What happens if the guest has no free receive buffer?** The device must drop the frame.
5. **NAT vs bridge?** NAT is L3/L4 rewriting so a private subnet shares the host's address; a bridge is an L2 switch. "Bridged networking" puts the VM on the physical LAN by adding the physical NIC to a bridge.
6. **Which header changes at each hop?** The Ethernet header at every hop; the IP header only where NAT rewrites it.
7. **Why TAP and not TUN?** The guest owns a MAC and does ARP, so we need layer 2.
8. **Why is the device model security-sensitive?** It parses structures in guest-controlled memory: validate every address, copy once, bound every chain walk (`dma.h`).
9. **Why release/acquire on ring indices?** To make sure the other side sees the entries before it sees the index; on ARM it is not automatic.
10. **What differs per platform?** The hypervisor API and the back-end; the front-end and the protocols do not. Multipass hides this behind a backend interface.
